### Instructions (account order = IDL order)

| Instruction | Args | Accounts |
| --- | --- | --- |
| `create_party` | party_id [u8;32], box_signer, challenge_secs u32, bond u64, require_member_sig bool | payer(w,s), host(s), party(w), mint, vault(w), host_token(w), token_program, system_program |
| `deposit` | amount u64 | payer(w,s), member(s), party(w), member_account(w), mint, member_token(w), vault(w), token_program, system_program |
| `request_close` | none | signer(s), party(w), member_account (optional) |
| `submit_state` | member Pubkey, nonce u64, balance u64, state_hash [u8;32] | party(w), member_account(w), instructions_sysvar |
| `finalize` | none | party(w) |
| `withdraw` | none | payer(w,s), party(w), member_account(w), wallet, mint, vault(w), wallet_token(w), token_program, associated_token_program, system_program |
| `withdraw_host` | none | payer(w,s), party(w), host, mint, vault(w), host_token(w), token_program, associated_token_program, system_program |

- `payer` is separate from `host` / `member` everywhere, so the treasury pays all fees and rent and
  players never need SOL (tested: member and host wallets hold 0 lamports throughout).
- `request_close`: host or box signer at any time; a member only after 6 h from party creation.
- `withdraw` / `withdraw_host` are cranks: anyone can call them, the destination is forced to be the
  member's (host's) own associated token account, created on the fly if missing.
- Events (Anchor `emit!`): `PartyCreated`, `Deposited`, `CloseRequested`, `StateSubmitted`,
  `Finalized`, `Withdrawn`, `HostWithdrawn`. Every event starts with the party address.

### Signature check in `submit_state`

The transaction must contain, before `submit_state`, Ed25519 program instruction(s) that verify the
127-byte message `"HUDDLE_STATE_V1" || party || member || nonce u64 LE || balance u64 LE || state_hash`
for the box signer, and for the member wallet too when `require_member_sig` is true. The program
rebuilds the message from its own arguments and the party address, reads the instructions sysvar,
and only counts signature entries whose three instruction indexes point at the Ed25519 instruction
itself (`0xffff` or its own index), reading key and message from that same instruction with bounds
checks. Both layouts are accepted: one instruction per signature (web3.js default) or one
instruction carrying both signatures over a shared message (what the client sends, 129 bytes smaller).

### Finalize design

The program cannot loop over Member accounts, so `submit_state` keeps two running sums on the Party:
`sum_claims` and `claimed_deposits` (a replaced claim subtracts the old balance first). At finalize:

```text
finalized_sum = sum_claims + (total_deposits - claimed_deposits)   // no claim = default to deposit
available     = total_deposits + bond
finalized_sum <= available : pay everyone in full, host_refund = available - finalized_sum
finalized_sum >  available : cut = true, payout_i = floor(effective_i * available / finalized_sum)
```

`withdraw` applies the formula per member. The pro-rata rounding dust is only known once everyone
has withdrawn, so `withdraw_host` pays `host_refund` on its first call and, once
`withdrawn_count == member_count`, sweeps whatever is left in the vault. Host total = exactly
`settleClaims().hostRefund`. Verified against `settleClaims` in Rust unit tests, a 500-round fuzz
in Vitest and on-chain.

## TypeScript client (`packages/solana-client`)

`createSettlementClient(mode, env)`: `points` -> mock; `vault` / `trusted` -> `VaultSettlementClient`
when `SOLANA_RPC_URL`, `HUDDLE_PROGRAM_ID`, `USDC_MINT`, `TREASURY_SECRET_KEY` are all set, else one
warning and the mock. Optional: `SOLANA_CLUSTER` (`devnet` default, `localnet`), `SOLANA_WS_URL`.
A mainnet endpoint is refused.

Behaviour worth knowing (all tested):

- `createParty` is idempotent (same host + party id returns the existing address, no transaction)
  and tops the host wallet up from the treasury for the bond. `depositFromKey` tops up the same way.
- `prepareDeposit` returns the transaction message as base64; the phone signs those bytes with
  tweetnacl. It fails early with "insufficient USDC balance" if the wallet is short. Pending deposits
  are kept in memory, are one-shot and die with the blockhash (roughly a minute): on any failure the
  phone must call `prepareDeposit` again. They do not survive an engine restart.
- `requestClose` returns `challengeEndsAt` on the engine's clock (now + the window left on-chain),
  not the cluster's clock. `finalize` waits up to 20 s for the cluster clock before giving up with
  "challenge window still open".
- `finalize` pays the host refund in the same transaction when there is one; `withdraw` sweeps the
  dust to the host after the last member. `finalize` on an already finalized party just returns the
  payouts. Extra public methods: `withdrawHost`, `getParty`, `getMember`, `getMembers`,
  `partyAddressFor`.
- Errors use the mock's messages ("stale nonce", "invalid box signature", "already withdrawn", ...);
  failed transactions throw `VaultTxError` with the program error name in `.code`.

Mocked: nothing inside the real client. Without the four env variables the factory still returns
the in-memory mock.

## Decoding notes for the QuickNode Streams filter

Everything is in `packages/solana-client/src/decode.ts`, which has **zero imports** so it can be
pasted into the filter (strip the type annotations).

- `decodeHuddleInstruction(data, accountKeys)`: `data` is the instruction data (bytes, or the base58
  string JSON-RPC gives); `accountKeys` are that instruction's accounts as base58, in order
  (`ix.accounts.map(i => message.accountKeys[i])`). Returns `{ instruction, partyPda, member?,
  amount?, nonce? }` or null. Discriminators = `sha256("global:<name>")[0..8]`:

  | Instruction | Discriminator | partyPda | member | amount |
  | --- | --- | --- | --- | --- |
  | create_party | `[251,84,246,151,106,204,201,22]` | accounts[2] | accounts[1] (host) | bond, data[76..84] |
  | deposit | `[242,35,198,137,82,225,242,182]` | accounts[2] | accounts[1] | data[8..16] |
  | request_close | `[82,168,167,86,14,15,199,180]` | accounts[1] | accounts[0] (signer) | none |
  | submit_state | `[172,31,42,160,233,237,4,251]` | accounts[0] | data[8..40] | balance, data[48..56] |
  | finalize | `[171,61,218,56,127,115,12,217]` | accounts[0] | none | none |
  | withdraw | `[183,18,70,156,148,109,161,34]` | accounts[1] | accounts[3] | not in the data |
  | withdraw_host | `[103,247,115,166,187,165,7,18]` | accounts[1] | accounts[2] (host) | not in the data |

- The `withdraw` payout is computed on-chain, so take it from the `Withdrawn` event:
  `parseHuddleLogs(meta.logMessages, programId)` returns the decoded events (it only trusts
  `Program data:` lines logged while huddle_vault is the executing program), and `toChainEvent(ev)`
  gives `{ kind, partyAddress, member, amount }`. `instructionToChainEvent` does the same from an
  instruction. `subscribe()` uses exactly this path with `via: "rpc"`.
- Skip failed transactions (`meta.err != null`). A `submit_state` transaction also contains an
  Ed25519 program instruction: ignore instructions whose program is not `HUDDLE_PROGRAM_ID`.

## Decisions

- A1-1 `party_id` is 32 opaque bytes (padded or hashed engine id): a seed must be <= 32 bytes.
- A1-2 The vault is a PDA token account (`["vault", party]`), not an ATA: one less program in `create_party`.
- A1-3 Running sums + per-member pro-rata in `withdraw`, host dust swept at the end: the only way to mirror `settleClaims` without iterating accounts.
- A1-4 Separate `withdraw_host` crank, bundled into `finalize` by the client: keeps `finalize` free of token accounts so anyone can call it.
- A1-5 `payer` is a separate account in every instruction that creates accounts: players and the host key never need SOL.
- A1-6 Member close timeout is a constant (6 h from creation), not a `create_party` argument: keeps the PRD signature.
- A1-7 `challenge_secs` is capped at 7 days: a typo cannot lock a vault for years.
- A1-8 A first claim is accepted at any nonce (including 0); after that strictly higher: same rule as the mock.
- A1-9 Hand-rolled instruction encoding in the client, checked against the IDL with Anchor's coders in tests: keeps the Streams decoder dependency-free and avoids pinning the Anchor TS runtime to the 1.x IDL.
- A1-10 One Ed25519 instruction with both signatures over one message copy: smaller transaction; the program accepts the standard layout as well.
- A1-11 `challengeEndsAt` is reported on the local clock: a validator that slept was 55 minutes behind wall time in testing, and devnet drifts too.
- A1-12 On-chain tests are Vitest files in `packages/solana-client/tests`, run by `anchor test`: the repo root has no Solana dependencies and root config is not mine to edit.
- A1-13 Keys default to `./keys` (gitignored by name); for this run they went to `~/.config/huddle/devnet` because the worktree is temporary.
- A1-14 No dependencies added; `pnpm-lock.yaml` is untouched.

## Known limits

- A box signer colluding with one member can sign that member an inflated balance; the others are
  then cut pro rata once the bond is used up. This is the PRD design (the box cannot move funds, the
  bond is the deterrent), not a full state channel.
- Party and Member accounts and the vault are never closed, so their rent stays locked (about
  0.007 SOL per party plus 0.002 per member).
- External-wallet deposits (Solana Pay, P1) are not built.
